§ 0 — Ground already covered

Three prerequisites, all resolved

Xcode is not required. A probe target using MenuBarExtra and UserNotifications compiles cleanly against the Command Line Tools SDK 15.5. We build with SwiftPM, assemble the .app bundle from a script, and sign ad-hoc. No 15GB download.

The project has a home. /Volumes/2TB/claude-vault/projects/chotki, alongside design.md, checklist.md and mockup.html. Personal context lives in a gitignored file and never reaches the public repository.

The port is planned for, not deferred blindly. macOS ships first with SwiftUI. Swift compiles on Windows and Linux; SwiftUI does not — so core/ is a pure package importing only Foundation and SQLite, and the port becomes a UI rewrite rather than an app rewrite.

Two unretired risks, both tested in Phase 1. That a notification with actions delivers from an ad-hoc-signed bundle. And that core/ builds on Linux in CI — before there is anything to port, because portability that is never exercised is only ever intended.

The boundary is the whole strategy. Anything Apple-only inside core is a bug, not a shortcut.

§ 0b — Architecture

One core, one interface per platform

core/            Foundation + SQLite only — builds on all three
  Model/         Rule, Activation, Occurrence, LiturgicalDay
  Recurrence/    expansion, activation intersection, three-way edit
  Scoring/       weighting, streaks, prose generation
  Liturgical/    orthocal client, cache, jurisdiction
  Scheduling/    in-process scheduler; Notifier protocol
  Platform/      LaunchAtLogin, TrayPresenter protocols

macos/          SwiftUI — the only Apple-specific code
.github/        CI: build + test core on macOS AND Linux

Scheduling lives in core rather than in the OS. The app is tray-resident and always running, so an in-process scheduler decides when and a thin platform notifier only shows. That is portable, and it tests headlessly against an injected clock with no desktop present.

These three govern every later decision. Where a trade-off is unclear, resolve it toward these.

§ 1 — Principles

What the app must never do

Nothing is switched on by default. The bundled rules are a library you take from, one at a time. First launch invites you to pick two or three, not twelve.

Nothing you did is ever destroyed. Pausing a rule excludes those days from scoring rather than counting them against you. Deleting archives. The record of what you actually kept is permanent.

The reckoning is a setting, never an assumption. Jurisdiction is one value; every date-aware surface reads through it. Switching it changes no code.

Occurrences are written only when a day deviates. An untouched day has no row — absence is the default state, not a record.

Store all-day dates as calendar dates. A timestamp will shift a day under DST and the bug surfaces months later.

§ 2 — Data model

Four tables, SQLite via GRDB

Rule
  id, title, note, source            — who suggested it, and why
  recurrence                         — daily | weekly(days) | monthly(day)
                                        | liturgical(season|fastDay|feast)
  timeOfDay: Time?                   — nil means "anytime today"
  category, createdAt, archivedAt

Activation                          — many per rule; this is the pause mechanism
  ruleId, from: Date, to: Date?      — nil `to` means currently in force

Occurrence                          — written only on deviation from default
  ruleId, date: CalendarDate
  status: completed | completedLate | skipped | moved | cancelled
  completedAt: Date?

LiturgicalDay                        — cache, keyed by (date, reckoning)
  date, reckoning, fastLevel, fastException, abstentions
  feastLevel, commemorations, readings, fetchedAt

Everything else is computed. A day with no Occurrence row and a covering Activation is simply due — or, once its time has passed, missed.

This is the part that breaks if rushed. The three-way edit determines the schema; retrofitting it is a rewrite.

§ 3 — Recurrence and activation

Expansion, and the three-way edit

The engine expands rules into occurrences across a date range, intersected with activation periods. A day is scoreable only if some activation covers it.

Editing or deleting a repeating rule always asks three ways: this day only (writes an Occurrence exception), this and future (closes the current activation, opens a new one on the edited rule), the whole series (edits the rule in place). Deleting the series closes the activation and sets archivedAt — occurrences survive.

Cases the tests must cover

  • Monthly on the 31st, in a 30-day month, and in February
  • The DST transitions in both directions — a 06:30 task must stay 06:30
  • 29 February, and a rule created on it
  • A rule enabled today generating no history before its first activation
  • A paused stretch scoring as skipped, never as missed

The default is Julian on adherent numbers, not on any one jurisdiction. Confirm it against your own.

The app must never block on the network. A menu bar popover that spins is a menu bar popover you stop opening.

§ 4 — The liturgical layer

Jurisdiction, and a fourteen-day cache

The default reckoning is Julian, carried by roughly 110 million adherents — Russian, Serbian, Georgian, Jerusalem, Polish — against roughly 47 million on the Revised Julian calendar. The figures are soft, but the Russian Church alone outweighs every New Calendar church combined, so the ordering holds.

Jurisdiction
  name          — "ROCOR", "Georgian", "Antiochian" …
  reckoning     — .julian (default) | .revisedJulian
  endpoint      — orthocal.info/api/{julian|gregorian}/

A background task prefetches fourteen days ahead and writes to LiturgicalDay. Every read goes to cache first; the network is only ever a refill. Offline, the app shows what it has and marks the reading as cached — it never shows a spinner or an error where text should be.

From this layer the calendar gets fast and feast shading, rules get liturgical recurrence (fast days, seasons, great feasts), and the reading tab gets its content. Changing jurisdiction invalidates the cache and refetches; nothing else reacts.

Old-style dates

An optional secondary line — 19 August · 6 August o.s. — so a parish bulletin and a wall calendar can be reconciled at a glance.

Lead with the sentence, not the number. "Evening prayers slipped twice, both Fridays" is the part that changes anything.

No red, no "failed", no broken-streak shaming. A setting hides the number entirely.

§ 5 — Scoring

Weighted to the last thirty days

  • Only occurrences whose due time has passed are scored
  • Only days inside an activation period count at all
  • completedLate scores partial, not zero
  • skipped is excluded from both numerator and denominator
  • The last 30 days weigh heaviest; older days decay but never vanish
  • Per-rule streaks are tracked alongside the aggregate

The report generates prose first — which rules slipped, on which weekdays, and whether a pattern is visible — then the figure, then the per-rule breakdown.

Mark complete from the banner. This single affordance does more for adherence than the score does.

§ 6 — Notifications

Ten minutes before, and a bounded nag

Timed rules fire ten minutes ahead. Untimed rules repeat hourly until marked complete, subject to two limits: quiet hours (default 21:30–06:30) and a cap of four reminders, after which the rule goes quiet and lands in the report rather than buzzing all night.

Every notification carries two actions — mark complete and snooze an hour. Completion cancels all pending notifications for that occurrence immediately.

Popover width 380–420pt. Anything wider stops feeling like a menu bar app.

§ 7 — Interface

One popover, three tabs

Left click opens the popover; right click gives a quick menu — mark the next task done, snooze, open progress, quit. The menu bar icon is an eight-pointed cross supplied as a template image so macOS inverts it correctly in both menu bar appearances.

Rule holds the month grid and today's list. Reading holds the day's commemoration and scripture. Progress holds the report, which can also open detached into a proper window where a month grid and a percentage do not have to share 400 points of width.

Palette: deep charcoal ground, byzantine gold for the day and for completion, muted violet for fasting seasons, ochre red for liturgy days. Restraint is the point — ornament reads as kitsch at 12pt.

Each phase ends in something runnable, and every core phase ends green on Linux too.

§ 8 — Build order

Eight phases

01

Foundations, and two spikes

Workspace, bundle script, ad-hoc signing, template icon, launch at login. Then immediately: prove a notification with actions delivers, and prove core/ builds and tests on Linux in CI.

proof green CI on macOS and Linux; a notification whose actions call back.
02

Core — store and recurrence

Storage behind a repository protocol, the four tables, expansion across activation periods, the three-way edit, JSON export. No interface.

proof the DST, month-end and leap-day suite passes on both platforms.
03

Core — liturgical layer

Jurisdiction, orthocal client for both reckonings, fourteen-day prefetch, cache, offline fallback, liturgical recurrence. Tests run against recorded fixtures so CI stays offline.

proof correct fast level for 13 Jan 2027 under each reckoning; full function with the network off.
04

Core — scheduling

In-process scheduler, ten-minute lead, bounded hourly repeats, quiet hours, the Notifier protocol with an actions capability flag so a platform lacking them degrades rather than falls silent.

proof a simulated month of ticks fires correctly, headless, against an injected clock.
05

macOS interface

Popover, tab chrome, month grid with fast and feast shading, today's list, add and edit sheets, the rule library, right-click menu, and the macOS notifier wired to the core scheduler.

proof a rule can be taken on, kept, edited, paused and resumed entirely through the interface.
06

Progress

Scoring, weighting, streaks, the prose summary generator, the report view, and the setting that hides the number.

proof a paused stretch leaves the score unmoved; a rule enabled today reports no prior misses.
07

Reading tab and polish

Commemoration, readings, cached-state marker, bundled patristic texts, first-run onboarding, prayer rope counter.

proof clean install to first kept rule, walked end to end.
08

The port

Not scheduled — listed so the shape is known while macOS is built. Windows: WinUI tray, ICO, toast actions. Linux: StatusNotifierItem, libnotify, and a GNOME shell extension, which is a platform limitation no stack choice avoids.

proof everything in core reused unchanged. Anything that is not is a bug in the boundary.

Only the first of these needs an answer from outside the app.

§ 9 — Still open

Three decisions

Which reckoning does your parish keep?

Julian is the default on adherent numbers, so for most Orthodox this confirms rather than changes it. Still the one input the app cannot derive for itself.

Quiet hours default

21:30–06:30 unless morning prayers sit earlier, in which case the window should shift with them.

Should feast days propose tasks?

Agreed in principle — the question is whether a proposed Liturgy on a great feast appears automatically or waits behind a prompt.

Named so they are choices, not oversights.

§ 10 — Out of scope

Not in the first version

  • iCloud or cross-device sync — the store is local, backed up by JSON export
  • Any network call other than orthocal; no analytics, no account, no telemetry
  • A mobile companion
  • Notarisation and store distribution — ad-hoc signed
  • Multiple profiles or households
